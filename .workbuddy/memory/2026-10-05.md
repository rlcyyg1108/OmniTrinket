### 崩溃修复：Curios Mixin InvalidAccessorException（关键经验！）
- 现象：`runClient` 启动即崩，`No candidates were found matching f_19803_:Z in
  net/minecraft/world/entity/Entity for curios.mixins.json:AccessorEntity`。
- 根因：项目用 **official 映射**，Curios 发布 jar 的 `curios.refmap.json` 存的是 **SRG 名**
  （`f_19803_`）。`fg.deobf()` 只 remap 字节码的类/字段引用，**不会改 refmap JSON**，
  于是 mixin 拿着 SRG 名去 official 命名的类里找字段 → 找不到。
- 修复：`build.gradle` 的 `runs.configureEach` 里加：
  ```gradle
  property 'mixin.env.remapRefMap', 'true'
  property 'mixin.env.refMapRemappingFile', "${projectDir}/build/createSrgToMcp/output.srg"
  ```
  让 mixin 加载时按 output.srg（SRG→official 方向）实时翻译 refmap。
  已验证 `build/createSrgToMcp/output.srg` 内含 `FD: .../Entity/f_19803_ .../Entity/firstTick`。
  （注意方向：必须是 `createSrgToMcp`，不是 `createMcpToSrg`。）
- 依赖仍需 `fg.deobf("top.theillusivec4.curios:curios-forge:...")`，两者配合才有效。
- 副作用：修完 AccessorEntity 后，`MixinInventory` 可能仍报
  `@Shadow field f_35978_ was not located`——这是 Curios 自身 mixin 在 dev 环境的已知不兼容，
  **正式游戏/正式服务端不会出现**，dev 下如继续报需权衡是否忽略。

**Mixin 基础设施（重要，ForgeGradle 6 配置踩坑记录）**：
1. `minecraft { }` 里 **没有 `mixin { config ... }` 这个 DSL**（该 API 在 FG6 不存在，
   写了会 `Could not find method mixin()` 直接构建失败）。改为在 `jar` 任务的
   manifest 里加 `'MixinConfigs': 'omnitrinket.mixins.json'`。
2. 光有 manifest 不够：**refmap 不会自动生成**（构建成功但 jar 里无 `.refmap.json`，
   运行时会因找不到 SRG 名崩溃）。必须在 dependencies 里显式加
   `annotationProcessor 'org.spongepowered:mixin:0.8.5:processor'`。
3. 加了 AP 后还需在 `tasks.withType(JavaCompile)` 传参，否则报
   `Unable to locate obfuscation mapping for @ModifyVariable target ...`：
   ```gradle
   options.compilerArgs += [
       "-AoutRefMapFile=${project.buildDir}/resources/main/omnitrinket.refmap.json",
       "-AmappingTypes=tsrg",
       "-AdefaultObfuscationEnv=searge",
       "-AreobfTsrgFile=${project.buildDir}/createMcpToSrg/output.tsrg",
       "-AoutTsrgFile=${project.buildDir}/tmp/compileJava/omnitrinket.tsrg"
   ]
   ```
   - **`-AmappingTypes=tsrg` 是关键**：mixin AP 的 FG3 obfuscation service 只有在该
     option 含 "tsrg" 时才注册（javap 反编译 `ObfuscationServiceFG3.getObfuscationTypes` 证实）。
     不传则只加载 MCP 服务，只认 srg → 报找不到映射。
   - 选项名必须是 `reobfTsrgFile` / `outTsrgFile`（**不是** `tsrgFile`/`mappingFile`，
     写了会静默变成"未被处理程序识别"的警告并在后续报错）。
   - 映射文件用 `build/createMcpToSrg/output.tsrg`（TSRG2 格式，MCP→SRG 方向）。
   - 成果验证：`build/resources/main/omnitrinket.refmap.json` 内容为
     `"updateLightTexture": "Lnet/minecraft/client/renderer/LightTexture;m_109881_(F)V"` ✅
4. `omnitrinket.mixins.json` 放在 **`src/main/resources/` 根**（不放 META-INF），
   `"package": "com.rlcyyg1108.omnitrinket.mixin"`，`refmap` 指向 `omnitrinket.refmap.json`，
   mixin 类列在 `"client"` 数组（因为 LightTexture 是纯客户端类）。

### 奔跑模块修正 + UI 模块（用户反馈后调整）

**用户反馈三处问题，已全部修正**：
1. 要的是"走路和奔跑都 2 倍"（之前只在奔跑时生效）
2. 奔跑时 FOV 被拉太大
3. 2 倍跳跃没有默认生效（之前也只跟着奔跑走）

**修正后语义**：
- `SprintEvents.tick` 现在**无条件**（只要佩戴 + 总开关开）挂两个修饰符，
  不再判断 `isSprinting()`。走路 / 奔跑共用 `MOVEMENT_SPEED`，乘倍率即两态通吃。
- 跳跃 `JUMP_STRENGTH` 也就常驻生效。
- 新增配置 `Config.COMMON.lockFov`（默认 true）。

**FOV 问题根因（重要，javap 反编译确认）**：
原版 `AbstractClientPlayer.getFieldOfViewModifier()` 里：
```
fovModifier *= ((movementSpeed / abilities.getWalkingSpeed()) + 1.0F) / 2.0F;
```
我们把 MOVEMENT_SPEED 翻倍后该系数从 1.0 → 1.5，所以视野被拉大。
**Forge 提供了免 Mixin 的钩子**：`ComputeFovModifierEvent`
（在 `ForgeHooksClient.getFieldOfViewModifier` 里 post，含 `getNewFovModifier/setNewFovModifier`）。

**对策**（`feature/impl/SprintFovHandler.java`，纯客户端）：
对原版公式求逆，把"由速度加成引起的 FOV 增量"精确扣除：
```
r  = currentSpeed / walkingSpeed
vanillaFactor = (r + 1) / 2
targetFactor  = (r / multiplier + 1) / 2
correction    = targetFactor / vanillaFactor
event.setNewFovModifier(event.getNewFovModifier() * correction)
```
其他 FOV 来源（弓、望远镜、受伤、飞行）全部原样保留；用弓/望远镜时不干预。

**FOV 二次修复（`SprintFovHandler` 重写）**：
- 旧版 `ratio/multiplier` 与"只扣自己那份"的算法都依赖 `ComputeFovModifierEvent`
  真的被 post。实测失效 → 说明**该事件在这台环境的渲染路径里没进来**
  （无法在本地验证，只能按"两条路都铺"来做）。
- 现在改为**双保险**：
  1. **主路径** `ComputeFovModifierEvent`：精确修正，公式整理为通用形式
     `系数(A) = (A + W) / 2W`（`A` = MOVEMENT_SPEED 属性值，`W` = walkingSpeed），
     把 A 换成 `A - credited` 再取比值：
     ```
     ourBonus   = (倍率 - 1) * baseSpeed        // baseSpeed = 属性默认值 0.1
     credited   = min(max(0, A - baseSpeed - W), ourBonus)
     correction = (A - credited + W) / (A + W)
     ```
     并加 `if (getNewFovModifier() < 0.999F)` 防重复扣。
  2. **兜底** `ViewportEvent.ComputeFov`（`EventPriority.LOWEST`）：
     用 **FOV 设置值本身**当"无加成基准"（`Minecraft.getInstance().options.fov().get()`），
     发现 `event.getFOV() > cleanFov` 就 `setFOV(cleanFov)`。
     常驻奔跑加速恰好对应原版"跑动时把 fov 设置抬到 1.1 倍"的行为，压回设置值
     就等于"奔跑时与原版不奔跑时一致"。
     **只在 `ourModifierActive(player)` 时才比对**（读属性上的 `SPEED_UUID` modifier），
     摘下饰品当 tick modifier 被清 → 压制立即解除，不会有"摘了还锁着"的副作用。
  3. `TickEvent.ClientTickEvent`(END) 维护快照有效性（换人 / 改 fov 设置时作废重建）。
- ⚠️ **踩坑**：`GameRenderer#getFov(Camera, float, boolean)` 是 **private**，
  不能用来取样（编译报 `private 访问控制`）。改用 `options.fov().get()`。
- ⚠️ 仍未实机验证。若这条兜底也无效，下一个怀疑点是 `ViewportEvent.ComputeFov`
  的 `usedConfiguredFov()` 过滤，备选改 Mixin `GameRenderer`。

`Player`/`LivingEntity` 的跳跃路径里**完全不读**（只有 `AbstractHorse` 读）。
⇒ 之前挂在 JUMP_STRENGTH 上的修饰符对玩家毫无作用。

**修复**：删掉 JUMP_STRENGTH 修饰符，改用 Mixin：
- 新建 `mixin/PlayerJumpMixin` —— `@Inject(method="jumpFromGround", at=@At("TAIL"))`
- `Player.jumpFromGround`（SRG `m_6135_`）确为 Player 覆写（refmap 验证 ✅）
- TAIL 处把 `deltaMovement.y *= sqrt(高度倍率)`（高度 ∝ v²，故开方）
- `SprintEvents.jumpVelocityScale(Player)` 提供倍率，未佩戴/关开关/≤1 时返回 1.0（不动原版）

#### Bug② 飞行飞不起来 —— 根因是 mayfly 没同步给客户端
原版双击跳跃链路：客户端 `LocalPlayer.aiStep` 检测双击 → 置 `abilities.flying=true`
→ 发 `ServerboundPlayerAbilitiesPacket` → 服务端 `handlePlayerAbilities` 校验
`packet.isFlying() && abilities.mayfly` 才接受。
之前 `FlightEvents` 只写了 `abilities.mayfly = true`，**从未 `onUpdateAbilities()`**，
客户端 LocalPlayer 的 mayfly 一直是 false ⇒ 双击被拒 ⇒ 飞不起来。

**修复**：`FlightEvents.tick` 加 `grantedChanged` 标记（mayfly 或 flying 被改动时置 true），
末尾 `if (grantedChanged && player instanceof ServerPlayer sp) sp.onUpdateAbilities();`
（`onUpdateAbilities()` 在 `ServerPlayer`/`LocalPlayer`，**不在 Player**，必须强转）。
`revoke()` 同样补 `onUpdateAbilities()`。

#### Bug③ FOV 固定失效 —— Forge 两个事件都不被 post，改 Mixin

- 新建 `mixin/AbstractClientPlayerFovMixin` —— `@Inject(method="getFieldOfViewModifier", at=@At("RETURN"), cancellable=true)`

- 旧的 `SprintFovHandler` 事件注册全部删除，`TickEvent.ClientTickEvent` 快照逻辑也删了

#### ★ 关键反编译结论（本轮最大收获）

**1) `Player.getFlyingSpeed()` 才是飞行速度的唯一出口**（SRG `m_274460_`，protected）
```
if (abilities.flying && !isPassenger())
    return isSprinting() ? abilities.getFlyingSpeed() * 2.0F : abilities.getFlyingSpeed();
return isSprinting() ? 0.026F : 0.02F;
```
⇒ ①**原版自己就已经对"冲刺飞行"硬编码 ×2**；
   ②`Player.travel` 的飞行分支只做 `super.travel()` + `Y*0.6` 阻尼，真正移动在
   `LivingEntity.travel` 用 `getFlyingSpeed()` 当 `moveRelative` 的 amount（水平垂直共用）。
⇒ **推翻旧架构**：不再 `ci.cancel()` travel（那会跳过 Y 阻尼/落地重置/姿态标记，
   手感崩坏），改为 `PlayerFlyingSpeedMixin` 在 `getFlyingSpeed()` 的 RETURN 乘倍率。
   倍率里先除掉原版那 2 倍（`FlightSpeedHandler.VANILLA_SPRINT_FLY_FACTOR`），
   使"加速飞行"完全由 `flyBoostMultiplier` 控制（默认 2.0 → 恰好 ×2）。
- 注意：`m_6113_` 是 **`getSpeed()`**（返回 MOVEMENT_SPEED），别混淆

**2) `Player.getDestroySpeed(BlockState)`**（SRG `m_36281_`，唯一重载，单 return）
结尾只有两处惩罚，**没有飞行加成**（旧注释是错的）：
```
if (isEyeInFluid(WATER) && !hasAquaAffinity) speed /= 5.0F;
if (!onGround())                              speed /= 5.0F;
```
⇒ `PlayerEvent.BreakSpeed.getOriginalSpeed()` 拿到的已是惩罚后的值，
   旧代码 `setNewSpeed(getOriginalSpeed())` 等于没做 → 这是"挖掘不减速无效"的根因。
   改为 `mixin/PlayerDestroySpeedMixin` 在 RETURN 把两次 ÷5 乘回来。
   `SurvivalEvents.onBreakSpeed` 一并删除（它同样无效），两个开关在同一个 Mixin 里
   用布尔合取判定，**避免同时打开时乘出 25 倍**。

**3) `LivingEntity.getJumpPower()`**（SRG `m_6118_`，protected，单 return）
`= 0.42F * getBlockJumpFactor() + getJumpBoostPower()`，被 `jumpFromGround` 写入
`deltaMovement.y`。旧实现注入 `Player.jumpFromGround` 的 TAIL 无效 →
新建 `mixin/LivingEntityJumpMixin` 直接改 RETURN（所有跳跃的唯一出口）。

**4) FOV：原版没有任何"冲刺"独立系数**
`AbstractClientPlayer.getFieldOfViewModifier()`（`m_108565_`）只有
`f *= (getAttributeValue(MOVEMENT_SPEED) / abilities.getWalkingSpeed() + 1) / 2`。
原版奔跑之所以拉大 FOV，是因为奔跑给 MOVEMENT_SPEED 挂了 ×1.3 修饰符。
⇒ `SprintFovHandler` 改为**用 `SprintEvents.SPEED_UUID` 反查自己挂的修饰符**，
拿 `instance.getBaseValue() * ourModifier.getAmount()` 当"自己那份额度"，
从属性值里减掉后取比值：
`correction = (attribute - ourBonus + walkSpeed) / (attribute + walkSpeed)`
（比旧的 min(totalBonus, ourBonus) 更精确，且摘下饰品立即恢复原版）
`SprintEvents.SPEED_UUID` 由 private 改 **public**。

**5) 伽马 Mixin 打错了局部变量**
`LightTexture.updateLightTexture(float)`（`m_109881_`）在 gamma 之前已经写过 3 次 float：
```
offset 45: fstore_3  (skyDarken)  ← 旧代码 ordinal=0 命中的是这里！
offset 54: fstore 4  (1.0F)
offset 66: fstore 4  (f*0.95+0.05)
offset 87: fstore 5  (options.gamma().get())  ← 真正的 gamma
```
⇒ `ordinal` 由 0 改 **3**。（曾考虑 `@Redirect` 那次 `OptionInstance.get()`，
   但 Mixin 对 static/non-static handler 的规则不能本地确证，`@ModifyVariable` 更稳。）

### 本轮重构（对齐参考实现）

**A. 飞行速度彻底改走原版通道**
- `FlightEvents.tick()`（服务端，每 tick）：`abilities.setFlyingSpeed(0.05 × 倍速 × 冲刺修正)`
  → 变化时 `ServerPlayer.onUpdateAbilities()`
  → 原版 `ClientboundPlayerAbilitiesPacket(Abilities)` 帮我们同步（反编译确认该包**含 flyingSpeed**）
- **删除 `mixin/PlayerFlyingSpeedMixin`**（不再需要拦截 `getFlyingSpeed()`）
- **删除 `FlightEvents.applyFlySpeed()`**（`Attributes.FLYING_SPEED` 与玩家飞行速度无关，
  玩家读的是 `Abilities.flyingSpeed`；`Abilities` 构造器里硬编码 0.05f / walkingSpeed 0.1f）
- 冲刺修正：`targetFlyingSpeed()` 在冲刺时乘 `flyBoostMultiplier / 2`，
  让原版自己那个 ×2 把最终倍率还原成正好 `flyBoostMultiplier`（默认 2.0 = ×2），避免变 ×4

**B. 垂直倍率换注入点**（`mixin/EntityMoveRelativeMixin`，替代原 `PlayerTravelMixin` 里的 ModifyVariable）
- 旧做法改 `travelVector.y` 无效：`Entity.moveRelative` 内部
  `(lengthSqr > 1 ? relative.normalize() : relative).scale(amount)` 会把超长向量归一化回来，
  纯垂直 (0,1,0) 乘倍率后长度 >1 → 被抹掉
- 新做法：`@Inject(method="moveRelative", at=@At("TAIL"))`，把"这一次新增的 Y 分量"放大
  `addedY = normalizedY × amount`，`delta.y += addedY × (垂直倍率−1)`；只改增量，水平/摩擦/阻尼不动
- ⚠️ 不能用 `LivingEntity.getFrictionInfluencedSpeed()` —— 它是 **protected**，
  mixin 类跨包访问会**编译失败**（mixin 类在编译期不 extends 目标类）

**C. FOV 公式修正（`SprintFovHandler`）**
原版 `AttributeInstance.calculateValue()`：
`value = (base + ΣADDITION) × (1 + ΣMULTIPLY_BASE) × Π(1 + MULTIPLY_TOTAL)`
旧代码用 `value - baseValue×amount` 减常数 → 原版奔跑的 ×1.3 是 MULTIPLY_TOTAL，
会和我们的 MULTIPLY_BASE 相乘，导致奔跑时算错（0.26−0.1=0.16，正确是 0.13）。
改为乘法分解：
`sumMb = Σ MULTIPLY_BASE amount；clean = value×(1+sumMb−ours)/(1+sumMb)；ratio = (clean/W+1)/(value/W+1)`
验证：走路 0.2→0.1，1.5×(2/3)=1.0 ✓；奔跑 0.26→0.13，1.8×0.6389=1.15 ✓（= 原版）

**D. 档位显示改读原版同步值**
`ClientFlightSettings.currentMultiplier()` = `abilities.getFlyingSpeed() / 0.05`
（冲刺时再 `× 2 / flyBoostMultiplier` 除回来）。HUD 与设置界面都用它，
不再依赖自定义同步包的镜像（那正是"档位显示慢半拍/错档"的来源）。

**E. 根因：`run/config/omnitrinket-common.toml` 里 `sprint.enabled = false`**
"移动"模块总开关关着 ⇒ 移速倍率 / 跳跃倍率 / FOV 修正**三项全不生效**。
源码默认是 true，是这个旧 toml 的值把它关掉了。**已直接改为 true**。
排查此类"没效果"问题，先看 `run/config/*.toml`。

**F. UI**
- 面板尺寸从"正方形 = min(宽,高)−24"改成固定 `PANEL_W=460 / PANEL_H=320` 居中
  （原来在 1080p 上是 1056×1056 的巨大方块，单列会拉得极长）
- `ToggleWidget` 勾选框两种状态都画：`[✔]` / `[  ]`

# 第二轮重构（用户反馈：四修没修好的问题 = 实现方式有问题，大胆重构）

## 1. 档位改成 5 档：1 / 2 / 3 / 5 / 10
`FlightSpeeds.LEVEL_PRESETS = [1.0, 2.0, 3.0, 5.0, 10.0]`，默认仍是档位 2（=2 倍速）。

## 2. 移速 FOV：**换思路 —— 把分母一起放大**（删除所有 FOV Mixin）

### 为什么之前一直不对
原版 FOV 公式：
```java
f *= (getAttributeValue(MOVEMENT_SPEED) / abilities.getWalkingSpeed() + 1) / 2
```
旧做法给 `MOVEMENT_SPEED` 挂 MULTIPLY_BASE 修饰符（分子 ×N），分母不动 → 比值变 N。
再靠客户端 Mixin 事后还原，可是原版奔跑的 ×1.3 是 **MULTIPLY_TOTAL**、
会和 MULTIPLY_BASE 相乘，还原公式很难写对。

### 决定性发现（反编译）
```
Player.readAdditionalSaveData():
    this.getAttribute(Attributes.MOVEMENT_SPEED).setBaseValue((double)this.getAbilities().getWalkingSpeed());

Abilities.getWalkingSpeed() 全原版只有 3 处调用：
   1) Player.readAdditionalSaveData（上面那行：它才是移动速度的持久化载体）
   2) AbstractClientPlayer.getFieldOfViewModifier —— FOV 的【分母】
   3) 同方法的 NaN 保护
Player.getSpeed() = getAttributeValue(Attributes.MOVEMENT_SPEED)   ← 实际速度
```
⇒ 原版不变式：**`MOVEMENT_SPEED.base == Abilities.walkingSpeed`**，而 FOV 就是二者之比。

### 现在
```java
MOVEMENT_SPEED.base      = 0.1 × N     // 实际速度 ×N
abilities.walkingSpeed   = 0.1 × N     // FOV 分母同步
走路 FOV = (0.1N/0.1N + 1)/2 = 1.00    // 与原版完全一致
奔跑 FOV = (0.13N/0.1N + 1)/2 = 1.15   // 原版奔跑的 ×1.3 自动跟着走
```
- **删除 `mixin/AbstractClientPlayerFovMixin` + `SprintFovHandler` + `SPEED_UUID` 修饰符**
- `SprintEvents` 只干一件事：把 `walkingSpeed` 与 `MOVEMENT_SPEED.base` 同步设为 `0.1 × factor`，
  变化时 `ServerPlayer.onUpdateAbilities()`（walkingSpeed 走原版 Abilities 包同步）
- `ServerGamePacketListenerImpl` 里 **0 处** `getWalkingSpeed`，所以不会触发 anticheat（已核）
- `Player.getFlyingSpeed()` 的 else 分支返回字面量 `0.026F/0.02F`，**不读 walkingSpeed**（已核）

## 3. 无惯性：改用 GTLCore 的写法（客户端 tick）

参考实现（GTLCore `disableDrift`）：
```java
if (disableDrift && phase==END && side==CLIENT && player.xxa==0 && player.zza==0)
    player.setDeltaMovement(player.getDeltaMovement().multiply(0.5, 1, 0.5));
```

**旧实现为什么"没效果"**：打在 `Player.travel` 的 TAIL，判据是"传入的 travelVector 是否为 0"。
但 `ServerPlayer` 的移动由客户端权威决定，**服务端 tick 时传入的 travelVector 恒为 (0,0,0)**，
于是服务端每一 tick 都在清零水平速度，与客户端真实移动互相打架。

**现在**：`feature/impl/NoInertiaEvents`，`@Mod.EventBusSubscriber(value = Dist.CLIENT)`，
`PlayerTickEvent(END)` + `xxa==0 && zza==0` → `setDeltaMovement(0, y, 0)`。
（`xxa/zza` 是 `LivingEntity` 的 public 字段，客户端由 `KeyboardInput` 每 tick 写入、
`aiStep` 里 `*= 0.98` 衰减 ⇒ "有输入永远非 0 / 松手正好 0"，是稳定判据。）
删除 `mixin/PlayerTravelMixin`。

## 4. 夜视：彻底改成药水效果（删除伽马方案）
