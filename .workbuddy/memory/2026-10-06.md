# 2026-10-06 OmniTrinket 维护日志

## 本轮：修 5 个"要重新装备/重开界面才生效"与输入体验问题

用户一次提了 8 个问题，按难易度分三档处理。本轮完成 **🟢 简单 3 项 + 🟡 中等 3 项**，
🔴 难的两项（垂直倍率、跳跃）留到后续单独做。

---

## 🟢 1. N 键只能开设置界面、不能关

**根因**：`ClientEvents.onClientTick` 开头就是 `if (mc.screen != null) return;`，
界面打开时快捷键整段被跳过；而且 KeyMapping 的点击队列不会被消费，
关闭界面的那一瞬间反而会把攒下的点击一次性触发（"关了又弹开"）。

**改法**：
- `OmniTrinketSettingsScreen.keyPressed()` 里用
  `KeyBindings.OPEN_SETTINGS.matches(keyCode, scanCode)` 判定 N → 走 `onClose()`，
  与右下角"完成"按钮完全等价。**不能靠 `consumeClick`**。
- `ClientEvents` 在 `screen != null` 时新增 `drainKeybinds()` 把三个按键队列排空。

## 🟢 2. 触及距离改完要重新装备才生效

**根因**：触及范围写在 `TrinketFeature.collectAttributeModifiers()` 里，
那是 **Curios 的接口，只在装备/卸下时调用一次**。

**改法**：新增 `feature/impl/BuffEvents`，用 `PlayerTickEvent(END)` 每 tick 主动
`addTransientModifier` / `removeModifier`（与 `SprintEvents` 同一套模式）。
`BuffFeature` 不再实现 `collectAttributeModifiers`。

## 🟢 3. 夜视重新给予时黑屏一下

**先确认：代码里没有任何 `removeEffect`**，只有一次 `addEffect`。

**真因**：原版 `Minecraft.getNightVisionScale` 在剩余时间 **> 200 tick（10 秒）** 时
亮度恒为 1.0，掉到 200 以下就切成 `0.7 + sin(...)·0.3` 的闪烁公式（40%~100% 抖）。
（Minecraft Wiki 原文：*"效果剩余时间不足10秒时，屏幕会每10游戏刻在夜视强度40%~100%
之间不断闪烁"*）

原来 300 tick / 每 100 tick 补 ⇒ 剩余时间在 `300 ↔ 200` 锯齿，**谷底正好压在那条线上**，
两端差 1 tick 就掉进闪烁区 ⇒ "黑屏一下"。

**改法**：`NIGHT_VISION_DURATION_TICKS` 300 → **400（20 秒）**，间隔仍 100。
谷底变 300，离阈值 100 tick 余量，永远不会闪。**用户的直觉完全正确。**

- `PlayerSettings` 新增 `nightVision`（默认 true）+ 全部 `KEY_*` 常量
- `Config.nightVision` / `Config.flyLockedModeDefault` **删除**
- `KeyBindings.TOGGLE_NIGHT_VISION`（Z）+ `KeyActionPacket` 不动，
  改用新的 `SetPlayerSettingsPacket`
- `ClientEvents.toggleNightVision()`：先本地乐观更新再发包，HUD 弹提示
- 设置界面"夜视"开关改成 `addPlayerToggle`（读 `ClientSettingsCache`）

## 🟡 5. 锁定飞行随开随关

**根因**：`FlightEvents.tick` 里 `flyLockedModeDefault` 只在 `!settings.isFlyGranted()`
（首次佩戴）时读一次 ⇒ 必须重穿。

**改法**：`flyLocked` 变成纯 `PlayerSettings` 字段，删掉 `Config.flyLockedModeDefault`，
界面加"锁定飞行"开关（`addPlayerToggle`）。`FlightEvents` 里"锁定就强制
`abilities.flying = true`"那段本来就是每 tick 跑的，改完即生效。

## 🟡 6. 数值输入框（方案 A：内嵌原版 EditBox）

**根因**：旧 `NumberWidget` 只维护一个 `editBuffer` + 追加/退格，
**没有光标、没有选区，Ctrl+A / Home / End / 双击选词全无**。

**改法**（方案 A）：
- `NumberWidget` 内嵌 `net.minecraft.client.gui.components.EditBox`
  （`setBordered(false)` 只借用文字与光标绘制，美术样式不变；数值区宽度 56→72）
- 新增 `NumberWidget.EditHost` 接口，由 `OmniTrinketSettingsScreen` 实现
  `focusEditBox` / `blurEditBox` —— **EditBox 必须既 `setFocused(true)`
  又成为 Screen 的焦点对象，键盘事件才会派发给它**
- `layoutRows()` 里在行控件之后 `addRenderableWidget(nw.getEditBox())`
  （渲染叠在行背景之上、鼠标派发排在行控件之后 ⇒ 编辑中点数值区由 EditBox 接手光标定位）
- `clearContent()` 里连 EditBox 一起 `removeWidget`
- 进入编辑态自动全选（`setCursorPosition(len)` + `setHighlightPos(0)`）
- Screen 侧删掉自建的 `charTyped` / `keyPressed` 输入分支，改由 `super` 派发；
  额外拦 **Enter / Tab**（提交并退出输入态，避免焦点被移走后留下"还在编辑但没焦点"的残留）
- `mouseClicked` 增加：焦点在 EditBox 且点击不落在它身上 ⇒ 先 `commitAllEdits()`

⚠️ 兼容性坑：`AbstractWidget.setVisible(boolean)` 在 1.20.1 的存在性不确定，
统一改用 public 字段 `editBox.visible = ...`。

## 🟠 顺带做的架构收敛

**`SetFlightSpeedPacket` → `SetPlayerSettingsPacket`（补丁式 NBT）**

以前每加一个"每玩家字段"就要新造一个包并改协议（很容易漏注册）。
现在客户端只把要改的键塞进 `CompoundTag`，服务端按白名单逐项应用：

```java
SetPlayerSettingsPacket.ofFlag(PlayerSettings.KEY_FLY_LOCKED, true)
SetPlayerSettingsPacket.ofDouble(PlayerSettings.KEY_FLY_SPEED, 3.0)
```

服务端只接受 4 个键：`FlySpeedMultiplier` / `FlyVerticalSpeedMultiplier` /
`FlyLocked` / `NightVision`；**`FlyGranted` 这类服务端状态客户端永远写不了**。

**`ClientSettingsCache` 增加乐观写入** `setLocalBoolean` / `setLocalDouble`：
界面点一下立刻改本地镜像（零延迟），服务端回发的权威值会自然覆盖。
这同时**顺带修掉了"垂直倍率输入后重开界面显示被重置"的观感问题**。

## 追加：数值输入框"字飘"实机问题

**现象**：点一下数值区，数字像是"飘"进了一个白框里。

**根因**：`beginEdit()` 里做了 `setCursorPosition(len)` + `setHighlightPos(0)`
= 进编辑态就整段全选，而**原版 `EditBox` 的选中高亮是一块亮色矩形**，
画在无边框输入框上就变成"数字被塞进一个白框"。

**改法**：
1. 去掉自动全选，只把光标放到末尾；想全选按 Ctrl+A（Home/End/方向键/双击选词仍是原版行为）
2. `drawContent()` 里**每帧**重新 `syncEditBoxBounds()`，保证输入框精确盖在数值区上
   （只靠 `setX/setY/setWidth` 时同步一次不可靠 —— 那些回调的调用时机取决于宿主怎么摆控件）

## 追加：UI 按"期望图"对齐（侧栏加宽 + 面板加大）

用户补发了 P 出来的期望图。逐项比对后，**两张图唯一明确的差异是侧栏宽度**：

| | 期望图 | 实机（改前） |
|---|---|---|
| 侧栏按钮宽 / 面板宽 | **19.8%** | 12% |
| 内容行宽 / 面板宽 | **70.7%** | 74% |
| 行区高 / 面板高 | 49.2% | 49.7% |
| 侧栏区高 / 面板高 | 33.3% | 33.6% |

⇒ 垂直比例本来就一致，**只有水平方向的侧栏需要加宽**。

**反解公式**（以后改布局可直接复用）：
```
侧栏按钮宽 = SIDEBAR_W − 12
内容行宽   = PANEL_W − SIDEBAR_W − 34      // 34 = 8(contentX 偏移) + 12(MARGIN) + 6(滑条) + 8(滑条间距)
```
两式联立 ⇒ `PANEL_W ≈ 484`、`SIDEBAR_W ≈ 108`。
再按期望图宽高比 983:705 ≈ 1.39 ⇒ `PANEL_H ≈ 348`。

**已改**：`SIDEBAR_W 72→108`、`PANEL_W 460→484`、`PANEL_H 320→348`。
验证：行宽 342（够放"去除浮空挖掘速度惩罚"10 个字），内容区高 276 → 11 行，
五个类别全部不需要滚动；小屏时 `min(..., 上限)` + 滑条兜底。

# 跳跃高度 & 垂直飞行倍率 —— 完全重构（参考 Draconic Evolution 1.20.1）

## 参考对象
`参考资料/Draconic-Evolution-1.20/`（用户手动放进来的，**不要去上网找**）

**跳跃（`handlers/ModularArmorEventHandler.java:421-425`）—— 纯 Forge 事件，零 Mixin：**
```java
MinecraftForge.EVENT_BUS.addListener(ModularArmorEventHandler::onLivingJumpEvent);
private static void onLivingJumpEvent(LivingEvent.LivingJumpEvent event) {
    float jumpBoost = getJumpBoost(event.getEntity(), false);
    if (jumpBoost > 0 && !event.getEntity().isShiftKeyDown())
        event.getEntity().push(0, 0.1F * (jumpBoost + 1), 0);   // 加法
}
```
- `JumpData(double multiplier)` 默认 0.25 / 0.75 / 1.25 / 4.00，`combine` 是**相加**
- 我反编译确认：Forge 在 `LivingEntity.jumpFromGround()` 设置完 `deltaMovement.y` **之后**
  才触发 `ForgeHooks.onLivingJump`（字节码偏移 75）⇒ **事件触发时 `deltaMovement.y` 就是原版起跳初速**

**飞行：1.20.1 分支没有"垂直速度分离"功能，且它的属性路线不能照抄。**
- `getFlightSpeedAttribute()` 用 `Attributes.FLYING_SPEED` + `MULTIPLY_BASE(amount = speedModifier/2)`，
  源码里作者自己留了 `//TODO test this modifier`
- 而 `Player.getFlyingSpeed()` 读的是 `abilities.getFlyingSpeed()`、**不读那个属性** ⇒ 对玩家无效
- ⇒ 垂直倍率只能自研（已与用户确认路线：保留 Mixin 但改 client-only）

## 找到的真正根因（比"Mixin 打错"深一层）

**`sprintJumpMultiplier` / `sprintSpeedMultiplier` 原本放在 `Config.COMMON`。**
Forge 的 COMMON 配置**只在登录时从服务端同步一次**，设置界面在运行时改它**只改客户端**。
而跳跃是"客户端预测 + 服务端验证"的 ⇒ 两端按不同倍率起跳 ⇒
**服务端以位置异常为由把玩家拽回原高度 ⇒ 表现为"改了没反应 / 完全没效果"。**
（我之前一直以为 Mixin 目标错了，反编译证明目标是对的 —— 问题在数据层，不在注入层。）
