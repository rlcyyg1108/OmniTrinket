# 第三轮：垂直倍率真根因（★ 重要教训）+ 惯性回退 + UI 修正

## ★★★ 垂直倍率"完全没效果"的真根因（本项目最重要的一条结论）

用户实测反馈：**"游戏内的飞行速度倍率能对垂直方向起效，但这个单独的倍率不行"** ——
这句话直接指向了答案。

`Player.travel(Vec3)` 反编译还原（1.20.1，字节码偏移 139~207）：
```java
if (this.abilities.flying && !this.isPassenger()) {
    double d = this.getDeltaMovement().y;      // ① 记下进入 travel 时的 Y
    super.travel(input);                      // ② 复用地面移动逻辑
    Vec3 v = this.getDeltaMovement();
    this.setDeltaMovement(v.x, d * 0.6, v.z); // ③ ★★ Y 被无条件覆盖 ★★
    this.resetFallDistance();
    this.setSharedFlag(7, false);
} else {
    super.travel(input);
}
```

**第 ③ 行是致命的**：原版不管 `super.travel()` 算出多少垂直增量，
一律换成"进入 travel 前那一刻的 Y × 0.6"。

⇒ **任何在这行之前给垂直加速度的尝试都会被丢弃**：
- 第1 版打在 `Entity.moveRelative` 的 TAIL 补 Y 增量 → 被覆盖
- 第 2 版照抄 Better Controls 打在 `LocalPlayer.aiStep` 的 `getFlyingSpeed()`
  → 那段还要求 `isControlledCamera()` 且必须按着跳跃/潜行键才执行，平移飞行时根本不跑

⇒ 也解释了**为什么"飞行速度倍率"能影响垂直**：它改 `Abilities.flyingSpeed`，
而第③ 行的语义本来就是"垂直速度由 abilities 那一套间接控制"。

### 正确做法（当前实现）
`mixin/PlayerVerticalFlightMixin.java`：`@Mixin(Player.class)` + **`@ModifyArg`**
打在 `travel` 里那次 `setDeltaMovement(DDD)` 的**index = 1**（Y 入参），
用 `@Slice` 框住整个飞行分支（从 `Abilities.flying` 字段 → 到 `resetFallDistance` 调用）。

```java
@ModifyArg(method = "travel",
    at = @At(value = "INVOKE", target = "Lnet/minecraft/world/entity/player/Player;setDeltaMovement(DDD)V"),
    index = 1,
    slice = @Slice(from = @At(FIELD Abilities.flying:Z), to = @At(INVOKE Player.resetFallDistance()V)))
private double omnitrinket$applyVerticalMultiplier(double originalY) { ... return originalY * multiplier; }
```

**为什么用 `@ModifyArg` 而不是 `@Redirect`**：`travel` 后面还有多处
`setDeltaMovement`；`@ModifyArg` 只替换这一个调用点的一个入参，调用仍由原版执行。
`@Atop` **不能用** —— 它是 Mixin 0.8.6+ 才有的，且配套的 `Arg` 类
（`org.spongepowered.asm.mixin.injection.invoke.arg.Arg`）在 1.20.1 根本不存在
（已javap 确认）。

# 第四轮：修"点击输入框后数字飘到左上角且点不到"

## 症状
"点击输入框之后，数字会突然飘到左上角，这是无法更改数字，然后再点一下才能进行操作，修改完成之后归位。"

## 两个独立病因（同时存在，互相叠加）

### ① 主因：`onLeftClick` 吞掉了第一次点击
`NumberWidget.onLeftClick` 的"进入输入态"分支原来 `return true`，
而内嵌 `EditBox` 在 `rebuildContent()` 里是**加在行控件之后**的
（`addRenderableWidget(w)` 先、`addRenderableWidget(nw.getEditBox())` 后）。
`Screen.mouseClicked` 按 `children()` 顺序派发，**只有当行控件不消费事件时轮到 EditBox**。
⇒ 第一次点击只进入编辑态、EditBox 从未收到该点击 ⇒ 光标无法定位 ⇒ 表现为"点不动"，
必须再点一次（此时 `onLeftClick` 走 `if (editing && ...)` 分支 `return false`，才让给 EditBox）。

**修法**：该分支改成 `return false`（`NumberWidget.java:326`）。
⇒ **规律：内嵌子控件的宿主，必须 `return false` 把事件让出去。**

### ② 次因：EditBox 坐标在"渲染前"没有无条件对齐
`EditBox` 是独立 widget，绘制**不经过** `NumberWidget.drawContent`，
所以原先只在 `setX/setY/setWidth` 回调 + `drawContent`（编辑态）里同步坐标会漏：
切换类别 / 滚动时行控件被 `removeWidget` 再 `addRenderableWidget`，
**EditBox 是新对象**，在真正摆到行上之前就可能已可见 ⇒ 数字出现在 (0,0)。
加事件阶段与渲染阶段的先后顺序，还会让"进入编辑态的第一帧"用旧坐标渲染一次。

**修法**：
- `NumberWidget.alignEditBoxBeforeRender()`（public，供宿主调用）
- `OmniTrinketSettingsScreen.render()` 里在 **`super.render` 之前**调
  `alignEditingEditBoxes()` 统一对齐（805 行，紧邻 807 行的 `super.render`）

### 顺带加固
`beginEdit()` 里 `editBox.visible = rowVisible && this.visible`
—— 行在滚动边界不可见时宁可先不显示，避免"点得中却看不到光标"。

## 教训
原版 `EditBox` 嵌在自绘控件里这套方案有两个方向性的陷阱：
1. **事件派发顺序**：`addRenderableWidget` 的先后决定谁先收到点击，
   宿主必须显式让出；右键清空这类"子控件不需要的点击"才 `return true`。
2. **坐标同步时机**：子控件的绘制独立于宿主，必须在 `super.render` **之前**兜底对齐，
   不能只依赖 `setX/setY` 回调。

# 第五轮：垂直倍率照搬参考 + 修"字段互相影响"

## ① 垂直倍率：删掉自创方案，逐字照搬 Better Controls 1.20

用户明确要求："按 bt 那里参考的来做，不要自己发挥，不要被现在已存在的代码勿扰了你的思考"。

⇒ **删除** `mixin/PlayerVerticalFlightMixin.java`（我自己发明的
`@ModifyArg` 打在 `Player.travel` 的 `setDeltaMovement(x, d*0.6, z)` 上）。
⇒ **恢复** `mixin/LocalPlayerVerticalFlightSpeedMixin.java`，
其 `@Redirect` 的 `method` / `at` / `slice.from` / `slice.to`
与 `Better-Controls-1.20/mixin/HookClientPlayerVerticalFlightSpeed.java`
**逐字一致**（已用 grep 对比确认）。

**同时移除了一个自己加的、参考实现里没有的判定**：
`FlightSpeedHandler.verticalMultiplier()` 早期版本带资格过滤，现已删除。
理由：施加点的前置条件（正在飞行 + 按住跳跃/潜行键）**原版自己已经判过**，
我们只乘一个系数；再加额外过滤会连带排除某些分支，反而让倍率"看起来没反应"。

**教训**：用户要求"照参考做"时，不要在参考实现上叠加自己发明的判定/防挂逻辑——
那些额外约束恰恰是让效果消失的来源。

## ② 字段"互相影响"的根因（数值闪来闪去）

`OmniTrinketSettingsScreen.submitPendingSettings()` 原来是**累积式**打包：
把所有 `pending*` 字段一次性塞进同一个 `CompoundTag` 发出。

⇒ 玩家只调「移速」，但 `pendingJumpHeight` 还留着之前的值，
这个包把跳跃高度也发了上去；服务端处理完回发**整份** NBT，
`ClientSettingsCache.apply`整体覆盖 ⇒ 界面上另一个数值莫名跳动
（实机："移速和跳跃高度调整时数值会闪来闪去，好像在互相影响"）。

**修法**：新增 `sendField(String settingsKey, double value)`——
**改哪个就只发哪个**。四个 setter 全部改为
`setLocalDouble(...)`（乐观更新本地镜像）+ `sendField(自己的键, 值)`。
`resetAll` 里逐个调 4 次 `sendField`；`onClose` 不再重复发包
（每次改动已即时发，关闭时再发会让服务端多回发一轮整份 NBT，白白引起跳动）。
`pending*` 字段保留，但**不再参与发包**，只用于界面显示。

**规律：增量同步的补丁里绝对不能残留其它字段的旧值。**

## ③ 输入框位置：syncEditBoxBounds 改为绝对坐标一次设全

`syncEditBoxBounds()` 加了守卫：行控件自身宽高 ≤ 0 时**直接 return**
（构造时是 `0,0`，此时去摆 EditBox 会把它固定在 (0,0) 直到下次布局）；
并改为一次性设置 X / Y / 宽 / 高（不再依赖 `setX` 等回调链的间接同步）。

# ★★★ 第六轮：真正的根因是客户端崩溃（前五轮全部跑偏）

## 症状回顾
- 垂直飞行倍率「改不动，点完成后再开又变回 1」
- 数字点一下飘到左上角
- 移速与跳跃高度「互相影响、数值闪来闪去」

## ★ 根因：一行 `for`循环导致客户端每 tick 崩溃

`run/logs/latest.log:102/133`（日志里其实早就有答案，我却绕了五轮才去看）：

```
java.util.ConcurrentModificationException
    at java.util.HashMap$HashIterator.nextNode(HashMap.java:1597)
    at ...omnitrinket.network.ClientSettingsCache.clear(ClientSettingsCache.java:45)
    at ...omnitrinket.client.ClientEvents.onClientTick(ClientEvents.java:49)
[Render thread/ERROR] [net.minecraft.client.Minecraft/FATAL]: Unreported exception thrown!
```

**错误写法**（`ClientSettingsCache` 的 `clear()` 与 `apply()` 各一份）：
```java
for (String key : DATA.getAllKeys()) { DATA.remove(key); }   // ← 边遍历边删
```

javap 核实 1.20.1 `CompoundTag.getAllKeys()` 的实现：
```java
public Set<String> getAllKeys() { return this.tags.keySet(); }   // ← 内部 Map 的实时视图，不是拷贝
```
⇒ 迭代器与remove 冲突 ⇒ 抛异常。

**触发路径**：`ClientEvents.onClientTick` 里 `mc.player == null` 时**每 tick**调
`ClientSettingsCache.clear()`（ClientEvents 原第 49 行）⇒ 进世界瞬间进入崩溃循环
⇒ 客户端根本活不到"设置界面"阶段。

**⇒ 三个症状全是这一处的连带结果**：
发包 → 服务端回发镜像 → 客户端在崩溃循环里收不到 → `ClientSettingsCache` 永远停在
默认值 1 → "改不动 + 重开回1"；崩溃打断 `Screen.render` → widget 停在中间态 →
"数字飘左上角"；同理 → "数值闪来闪去"。

## 修法（3 处）

1. **`ClientSettingsCache.clear()` / `apply()`**：
   改成 `DATA.getAllKeys().clear();`（对视图 clear()，既不抛异常又确实清得掉 DATA，
   因为它就是 `tags.keySet()`）。
2. **`ClientEvents`**：加 `wasInWorld` 标记，只在"从有玩家变成没玩家"那一刻清一次，
   原来是无条件每 tick 清。
3. **`NumberWidget.endEdit`**：解析失败时把输入框内容刷回当前真实值
   （原先静默保持原值，玩家以为改成功了，点完成才发现没变）。

## ★★ 教训（最重要的一条）

**"改了 N 遍没效果"时，第一件事是去看 `run/logs/latest.log`，不是继续读源码猜。**
本项目连续 5 轮都在修 UI 布局、Mixin 注入点、同步时序，而真正的错误是
一个 `ConcurrentModificationException`——它连"客户端崩了"这种明显现象都掩盖成了
"UI 显示不对"。

**排查手法固化**：
```
1. run/logs/latest.log 里grep ERROR / FATAL / Exception
2. run/logs/debug.log 里有更完整的堆栈
3. 崩溃时优先相信日志，不要用推理替代证据
```

# 第七轮：UI 输入框改回原版 + 飞行速度拆成水平/垂直两个独立属性

## 一、"数字飘左上角"的真正原因（方向判断错了五轮）

**不是坐标错，是"对齐方式跳变"**：
- 非编辑态：数值由 `NumberWidget.drawContent` **居中**绘制
- 编辑态：改由 `EditBox` 绘制，而 **`EditBox` 恒为左对齐**

⇒ 点击瞬间数字从居中跳到靠左，看起来就是"飘过去了"；点完成回到居中，又"归位"。
与"点一下就这样，完成后归位"完全吻合。

**修法**：新增 `client/gui/CenteredEditBox extends EditBox`，**只覆写 `renderWidget`**
（文字/光标/选区都按数值区中心对齐），输入逻辑完全走原版
（Ctrl+A / Home / End / 方向键 / 双击选词 / 剪贴板全部保留）。
`EditBox` 的 `value/cursorPos/highlightPos/scrollPos` 都是 private，
所以加了 `mixin/AccessEditBox.java`（Accessor）暴露。

同时简化了焦点管理：删掉 `NumberWidget.EditHost` 接口，
改为 `OmniTrinketSettingsScreen` 里的 `justBeganEditing` 中转字段 ——
`onLeftClick` 内部只调`beginEdit()`（它拿不到 Screen），
焦点在 `super.mouseClicked` 返回后补设`setFocused(box)`。

## 二、飞行速度拆成两个独立属性（效仿 Better Controls 的思路）

| 旧 | 新 |
|---|---|
| `flySpeedMultiplier`（飞行倍速） | **`flyHorizontalSpeedMultiplier`**（水平飞行速度） |
| `flyVerticalSpeedMultiplier`（垂直速度倍率，默认 1.0） | **`flyVerticalSpeedMultiplier`**（垂直飞行速度，默认 **2.0**） |

NBT 键 `FlySpeedMultiplier` → `FlyHorizontalSpeedMultiplier`（旧存档自动回落默认值）。
**两者完全独立、并存**；X 键档位 `[1,2,3,5,10]` **只改水平**。

### 为什么不照抄 BC 的水平实现
BC 面向创造/旁观模式，它让 `abilities.flyingSpeed` 保持原版 0.05，
两个倍率都在客户端各自乘。我们是**生存 + 饰品授予飞行**，且需要
服务端权威（`Abilities` 写入 + 原版包同步 + HUD 靠它读档位），
所以**水平必须走原版通道**（服务端每 tick 写 `Abilities.flyingSpeed`）。

### 我们的方案（1 个 client-only Mixin）
```
服务端：Abilities.flyingSpeed = 0.05 × 水平倍率
        （冲刺时再乘 (加速倍率/2)，抵消原版 getFlyingSpeed() 里的 ×2）
        ⇒ 水平速度 = 0.05 × 水平倍率 ✓（原版通道，HUD 照旧）

客户端 Mixin（@Redirect + @Slice 打 LocalPlayer.aiStep 的垂直出口）：
        乘以「垂直 ÷ 水平」的比值⇒ 垂直速度 = 0.05 × 垂直倍率
```
**为什么用比值**：垂直出口和水平出口读的是**同一个** `abilities.getFlyingSpeed()`，
它里面装的是"水平"倍率，所以要乘 `垂直/水平` 换算。
新增 `FlightSpeedHandler.verticalRatio(Player)`（带除零保护：水平 ≤1e-6 时返回 0）。

## 编译错误修正：EditBox 的滚动字段叫 `displayPos`，不是 `scrollPos`

`@Accessor("scrollPos")` 报 `Could not locate @Accessor target`。
javap 核对 1.20.1 `EditBox` 的真实私有字段：
```
value / maxLength / frame / displayPos / cursorPos / highlightPos /
textColor / textColorUneditable / suggestion / responder / filter / formatter / hint
```
⇒ **没有 `scrollPos`**，横向滚动位置叫 **`displayPos`**（`BorderEditor` 与
`EditBox` 共用同一套字段命名）。已把 `AccessEditBox` 的两个 `@Accessor`
与 `CenteredEditBox` 里的调用同步改名。

# 第八轮：UI 全部改用原版控件 + 飞行系统严格照搬 Better Controls

用户指出参考资料里有**两份** BC，并要求"BC 怎么做你就怎么做"。
核对后发现我上一轮**只照抄了垂直那份**，水平那份自己改了判定逻辑。三处偏离：

| | BC 原版 | 我上一轮（错） | 现在（严格照抄） |

| `@Inject` 判定 | `me instanceof LocalPlayer localPlayer && localPlayer.getAbilities().flying` | `FlightSpeedHandler.isActive(self)` | **同 BC** |

**最严重的偏离**：`@Mixin(Player.class)` 打在**服务端也会执行**的类上。
BC 靠 `instanceof LocalPlayer` 这个**类型检查**天然把服务端挡在外面；
我换成逻辑判定 `isActive()` 后，**服务端玩家飞行+佩戴饰品时也会走进client-only 的 Mixin**。

`FlightSpeedHandler.horizontalMultiplier()` / `verticalMultiplier()` 内部
（不满足时返回 1.0），**不放注入点**——这样两个 Mixin 的判定风格一致，
且 `@Redirect` 的类型检查只负责"排除服务端"这一件事。

## BC 两份 Mixin 的对称结构（已 javap 核对 1.20.1 锚点成立）

```
水平 HookPlayerHorizontalFlightSpeed  @Mixin(Player.class) extends LivingEntity
  ① @Redirect "getFlyingSpeed" ← isSprinting()   slice: Abilities.flying → Abilities.getFlyingSpeed()
     （打掉原版硬编码的冲刺 ×2；1.20.1 里 isSprinting 出现 2 次，slice 必需）
  ② @Inject "getFlyingSpeed" @At(RETURN) cancellable → cir × 水平倍率

垂直 HookClientPlayerVerticalFlightSpeed  @Mixin(LocalPlayer.class) extends LivingEntity
  ① @Redirect "aiStep" ← Abilities.getFlyingSpeed()
     slice: Abilities.flying → LocalPlayer.setDeltaMovement(Vec3)
     （1.20.1 里该调用只出现 1 次，@Redirect 无歧义）
```

**注意**：Mixin 类 `extends LivingEntity` 的2 参构造器**永远不会被调用**
（Mixin 不参与实例化），它只是让 `(X)(Object)this` 转型后能直接用继承来的方法。
`Player` 实际构造器是 4 参、BC 照样这么写 —— 照抄即可。

**教训**：用户给参考资料说"照着做"时，要**逐项对齐**（类声明、构造器、
判定条件、注入点、注解选择），不要"参考思路后自己实现"——
自己加的判定逻辑往往正是让效果消失的原因。

## ★★ 决定性发现：BC 的 FlightHelper 有一个"生存模式陷阱"

```java

    if (player.isCreative()) { ... }
    else if (player.isSpectator()) { ... }
    else { return 1F; }      // ★★★ 生存模式直接返回 1.0 = 完全无效果

## javap 实证：1.20.1 水平飞行的唯一出口

```

`LivingEntity.travel()` → `handleRelativeFrictionAndCalculateMovement()` →
`getFrictionInfluencedSpeed()` → `getFlyingSpeed()`。

## ★★★ 关于 Mixin 加载的调查结论（虽然最终不用 Mixin 了，但结论值得留档）

**ForgeGradle 6 + dev 环境下，自定义 mixin config 无法通过任何方式注册**（逐个试过）：
| 方案 | 结果 |
|---|---|
| 顶层 `mixin { config }` | `Could not find method mixin()` on Project |
| `minecraft{}` 内 `mixin { config }` | 落到 dependencies{} 上，同样报错 |
| `MixinExtension.forProject(...)` | **FG 6.0.54 jar 里根本没这个类**（unzip 验证） |
| `mods { source jar }` | `ModConfig.source()` 只接受 `SourceSet` |
| `property 'mixin.config'` | 时机太晚，runClient 验证无效 |
| `mods.toml` 的 `[[mixins]]` | 只对正式 jar 有效，dev 环境不读 |
| 自己生成 manifest jar 挂 classpath | 未验证完|

**根因**：`mods { source sourceSets.main }`（MOD_CLASSES）把
`build/resources/main` + `build/classes/java/main` 作为**目录**挂 classpath，
目录没有 manifest，而 Forge 靠 manifest 的 `MixinConfigs` 属性发现 mixin config。

**诊断判据（下次遇到 Mixin 不生效，先查这两条）**：
1. `debug.log` 有没有 `Registering mixin config: <你的>.json`
   （`remapRefMap=true` 时会为每个已加载 config 打印 `Remapping refMap`）
2. 有没有自检日志证明代码真的执行了

用户反馈（附熔炉 GUI 截图作为风格参考）："去除你加的这个白底，改为原版样式，
滑条只在屏幕放不下所有选项时出现，滑条不滑动完成和重置全部，
开关按钮改为[√]/[ ]的样式而非文字，重置全部按钮只有字没有按钮。"

## ★ 先修的正确 bug（上一轮的根因）

```java
// 旧：totalContentHeight() 把底部按钮也算了进去
for (AbstractWidget w : rows) {
    if (w == resetAllButton) continue;   // ← 漏了 done 按钮
    h = Math.max(h, w.getY() + ROW_H - y);
}
```
`done` 在面板最底部，Y 最大 ⇒ 恒 > viewport ⇒ **maxScroll 恒 > 0**
⇒ 滑条恒出现，且 applyScroll 把两个底部按钮推出面板。

## 本轮改动

### 1. 原版容器风格面板（照熔炉 GUI 的经典配色）
```java
COLOR_OUTLINE   = 0xFF000000;  // 外描边（1px 黑）
COLOR_PANEL     = 0xFFC6C6C6;  // 底色（浅灰）
COLOR_HIGHLIGHT = 0xFFFFFFFF;  // 高光（上/左 1px 白）
COLOR_SHADOW    = 0xFF555555;  // 阴影（下/右 1px 深灰）
COLOR_TEXT      = 0x404040;    // 深灰字（原版在浅灰底上的标准字色）
```
`drawVanillaPanel()` 按上述顺序画：描边 → 底 → 高光(上左) → 阴影(下右)。

### 2. 面板高度自适应（滑条只在放不下时出现）
```java
int contentRows = rowCountOf(currentCategory);   // 每类行数，见下
int needed = TITLE_H + contentRows * ROW_H + PAD + FOOTER_H;
int avail  = Math.max(PANEL_H_MIN, this.height - 2 * MARGIN);
int h = Math.min(needed, avail);                 // ★ 放得下就贴合内容
```
`rowCountOf()`：飞行 6 / 移动 5 / 生存 6 / 增益 3 / 环境 4。
`maxScroll = max(0, contentH - viewport)`，为 0 时**不画滑条**。

### 3. 底部按钮固定不滚动
新增 `footerWidgets` 列表（重置全部 + 完成）。`applyScroll()` **只遍历 `rows`**，
底部按钮永远不在其中 ⇒ 位置固定。这是本次修复的关键结构改动。

### 4. 开关改 [√] / [ ]
用 `Button.builder` 构建，点击时翻转并调 `updateToggleTexts()` 刷新全部按钮文字：
```java
Component.literal(getter.getAsBoolean() ? "[\u221A]" : "[ ]")
```
（**不能用 `new Button(...)`**：构造器是 `protected`，跨包无法直接 new。）

### 5. 重置全部只有字
`ResetAllButton.renderWidget` 只 `drawString` 红字，无边框无底色。
悬停变亮红 `0xFFCC3333`。点击区仍为 60x20，二次确认逻辑保留（3 秒）。

### 6. 标题
`omnitrinket.gui.title` 改为「全能饰品 - 设置 UI」，面板顶部居中绘制。

## 校验
BUILD SUCCESSFUL；9 项需求逐条机械核对全部 ✓；无 CycleButton 残留。

## 教训
**"面板高度"与"内容高度"必须是两个独立概念。**
把底部按钮混进内容列表，就会同时污染「滚动范围」和「是否显示滑条」两个判断。
结构上就该分开：`rows`（可滚动内容）/ `footerWidgets`（固定）/ `sidebarButtons`（固定）。

# 第十九轮：设置 UI 六项修正 + 冲刺飞行速度改乘算

用户反馈（附截图，截图里「重置全部」红字压在「环境」按钮上 = 我上一轮引入的 bug）。

## ★ 上一轮引入的 bug（截图可见）

"面板高度随内容自适应"是错的：面板高度按**当前分类**内容行数算，
但**侧边栏固定 5 个分类按钮**。增益分类只有 3 行内容 ⇒ 面板算出 128px 高，
而侧边栏需要 144px ⇒ **侧边栏溢出面板**，「重置全部」压在「环境」上。

**修法**：改成**固定尺寸**，按所有分类的**最大行数**预留：
```java
private static final int MAX_ROWS = 6;   // 飞行 6 / 生存 6 / 移动 5 / 环境 4 / 增益 3
int neededH = TITLE_H + MAX_ROWS * ROW_H + PAD + FOOTER_H;
int h = Math.min(neededH, availH);
```

## 六项改动

### 1. 固定面板尺寸
见上。宽 440、高 = 22 + 6*24 + 8 + 26 = 200。

### 2. 「重置全部」= 真 Button + 红框
原来是自绘 AbstractWidget（纯红字）。改成 `Button.builder` 的**真按钮**，
在 `render()` 里给它套一圈红框：
```java
int x0 = resetAllButton.getX() - 1;  ... graphics.fill(..., COLOR_DANGER);
```

### 3. 二次确认改 ConfirmScreen 弹窗
**旧做法的缺陷（用户指出）**：点击后变「确认重置?」，3 秒内再点即生效
⇒ **连点两下就误触**（第一次点击后按钮位置没变，第二次点击落在同一位置）。
新做法：`minecraft.setScreen(new ConfirmScreen(...))` 模态弹窗，
确认/取消两个独立按钮，位置不同 ⇒ 不可能误触。
```java
minecraft.setScreen(new ConfirmScreen(confirmed -> {
    if (confirmed) doResetAll();
    minecraft.setScreen(this);
}, title, body, yes, cancel));
```

### 4. ★ 冲刺飞行速度：替换 → 乘算（重要功能修正）
```java
// 旧（错）：冲刺时直接用 flySprintMultiplier，丢掉了 flySpeedMultiplier
double m = player.isSprinting() ? flySprintMultiplier : flySpeedMultiplier;

// 新（对）：
double multiplier = Config.COMMON.flySpeedMultiplier.get();
if (player.isSprinting()) {
    multiplier *= Config.COMMON.flySprintMultiplier.get();  // 独立乘区
    multiplier /= 2.0D;   // 抵消原版 getFlyingSpeed() 里硬编码的冲刺 ×2
}
return (float) (VANILLA_FLYING_SPEED * multiplier);
```
⇒ 实际冲刺速度 = `0.05 × 飞行速度 × 冲刺飞行速度倍率`
lang 改名：`冲刺飞行速度` → **`冲刺飞行速度倍率`**。

### 5. 右键输入框（照 simpleinfo 改）
**我漏掉的关键一步**：右键清空后没有 `setFocused(box)`，所以光标没出现。
```java
// 右键
updatingFields = true;
r.box.setValue("");
updatingFields = false;
setFocused(r.box);      // ★ 出现光标，可直接输入
```
**失焦归一化**（照 simpleinfo 重写 setFocused）：
```java
@Override
public void setFocused(GuiEventListener listener) {
    GuiEventListener previous = getFocused();
    super.setFocused(listener);
    if (previous != null && previous != listener && previous instanceof EditBox box) {
        restoreNumberBox(box);   // 空/非法 → 还原真实值
    }
}
// 点输入框以外 → setFocused(null)（在 mouseClicked 里）
```
**`updatingFields` 保护**（照 simpleinfo）：`syncBox()` 写值前置 true，responder 里 `if (updatingFields) return;` 防回环。

### 6. 开关改回「开」/「关」，不带冒号
```java
private static Component onOff(boolean on) {
    return Component.translatable(on ? "omnitrinket.gui.on" : "omnitrinket.gui.off");
}
```
lang 新增 `omnitrinket.gui.on` = 开 / `off` = 关。

## 校验
BUILD SUCCESSFUL；lang zh/en 各 69 条一致、零缺键；6 项需求 + 旧机制清理逐条核对全部 ✓。

## 教训
**"面板尺寸"与"内容行数"挂钩时，必须把固定部件（侧边栏/底部栏）的最大需求一起考虑。**
按当前分类的行数自适应 → 短分类会让固定部件溢出。
